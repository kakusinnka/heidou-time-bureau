# 黑豆时间管理局 · 产品书

> 一句话定位：一个用来记录"上次做某事是什么时候"的工具，用略带调侃的"审判/管理"口吻，帮你看清生活中被拖延的事项。

> 产品名：**黑豆时间管理局**　|　GitHub 仓库名：`heidou-time-bureau`

---

## 1. 产品概述

### 1.1 要解决的问题
生活中有大量"非每日、有周期性、但容易被忘记"的事项——剪头发、体检、换床单、联系父母、清洁空调滤网……它们不属于"待办清单"（没有截止日期），也不属于"习惯打卡"（不需要每天做），而是一类第三种任务：**周期性、靠回忆判断"该不该做了"的事**。目前人们靠大脑记忆或偶尔想起，容易长期拖延而不自知。

### 1.2 产品形态
一个网页应用（Web App），核心交互是：
- 给每件事建一张"档案卡"
- 记录每次完成的时间
- 页面直接告诉你：这件事已经过去多久了，是否已经"超期"

### 1.3 名字与调性
最终产品名定为**黑豆时间管理局**，GitHub 仓库名为 `heidou-time-bureau`。"时间管理局"的反差感是核心记忆点：用略带荒诞、审判式的机构口吻，包裹一个纯粹功能性的时间追踪工具。文案可以在"超期提示"上做文章（如"时间管理局对你的洗头频率提出警告"），作为与市面同类产品的差异化点，但**不做成负担或说教感**，避免变成新的心理压力源。

## 2. 核心功能设计（已确认）

### 2.1 记录粒度：存完整历史
- 每次打卡不是简单覆盖"上次时间"，而是作为一条历史记录追加。
- 基于历史记录可以计算：平均间隔、最短/最长间隔、间隔趋势。
- 数据结构上，"当前状态"（距今多久）应是从历史记录**派生计算**得出，而不是单独存储的字段，避免数据不一致。

### 2.2 期望周期（核心价值点）
- 每个事件可选填一个"期望间隔"（如 45 天、365 天）。
- 有期望周期的事件，用状态区分显示，**缓冲区间定为周期的 90%**：
  - **正常**：距上次完成时间 < 期望周期 × 90%
  - **该做了**：距上次完成时间 ≥ 期望周期 × 90% 且 ≤ 期望周期 × 100%
  - **已超期**：距上次完成时间 > 期望周期 × 100%
- 状态用颜色/视觉权重区分（如：灰/绿 = 正常，黄 = 该做了，红 = 超期），但避免"红色 = 罪恶感"的强烈警示设计，符合本产品"无愧疚感"的调性。
- **没有设置期望周期的事件**：只显示"已过去 N 天"，不做状态判断，同时在视觉上做**默认降权处理**——比如卡片使用更低对比度的配色、不显示状态色块，整体存在感弱于有周期设定的事件。这样列表混排时，用户的注意力会自然被有明确周期、且状态异常的事件吸引，无周期事件更像是一个"纯记录"而非"待关注项"。

### 2.3 分类（已确定）
- 分类**需要配图标/emoji**，每个分类一个符号，用于卡片和列表中快速视觉识别。
- 支持用户自建分类（自建分类也需选一个 emoji），不强制使用预设。
- **最终确定 4 个预设分类**：

| 图标 | 分类 | 示例事项 |
|---|---|---|
| 🩺 | 医疗健康 | 体检、洗牙、看医生、拉伸理疗 |
| 🧴 | 个护美容 | 剪头发、护肤、换牙刷、美甲 |
| 🏠 | 居家清洁 | 换床单、深度清洁、空调滤网、报警器电池 |
| 👨‍👩‍👧 | 社交家庭 | 联系父母、朋友聚餐、家庭活动 |

### 2.4 打卡方式
- **一键打卡**：主要交互路径，点击即记录"现在"为最新一次完成时间，操作路径要短。
- **补录历史**：支持手动选择过去的某个日期作为一次完成记录（用于回忆起"其实上个月就做过"的情况），同时用于首次创建事件时录入起始数据。
- 支持对错误记录的撤销/删除。

### 2.5 排序与展示
- 首页默认排序：**按超期程度从高到低**排列，而非按创建时间或字母顺序——最需要关注的事排在最前。
- 展示形式：卡片列表（每张卡片显示：事件名、分类、已过天数、状态颜色、期望周期）。
- 支持切换排序方式（如按分类分组、按最近完成排序）作为次要功能。

### 2.6 提醒：明确不做
- **不做主动推送提醒**。用户需要主动打开页面查看状态。
- 原因：网页本身做主动通知推送成本高（需 PWA + 通知服务），且与产品"无压力、不打扰"的调性相符——它是一个"你想起来的时候去看"的工具，而不是"来找你"的工具。

## 3. 数据存储方案

### 3.1 约束条件
- 部署平台：**GitHub Pages**（纯静态托管，不含后端服务器）。
- 需求：**支持换设备后能看到同一份数据**，而非单设备本地存储。

### 3.2 方案对比

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 纯 localStorage** | 数据存在浏览器本地 | 实现最简单，零依赖 | 换设备/清缓存即丢数据，不满足需求 |
| **B. 手动导出/导入 JSON** | 用户手动下载数据文件，在新设备导入 | 无需任何账号体系，数据完全自主可控 | 不是自动同步，操作繁琐，容易忘记备份 |
| **C. 以 GitHub 仓库/Gist 作为数据库** | 用户用自己的 GitHub 账号登录（OAuth 或 Personal Access Token），数据通过 GitHub API 读写到一个仓库文件或 Gist 中 | 免费、不需要额外的后端服务、和 GitHub Pages 部署天然契合、数据归属清晰（就是你自己仓库里的一个文件） | 需要处理 GitHub 授权流程和 API 调用逻辑，有 API 频率限制，首次配置略复杂 |
| **D. 第三方 BaaS**（如 Firebase / Supabase 免费层） | GitHub Pages 只托管前端页面，数据读写走第三方数据库服务 | 同步体验最流畅、有现成的账号体系和实时同步能力 | 引入了 GitHub 之外的第三方依赖和账号体系，超出免费额度需要付费 |

### 3.3 最终方案：C + B 组合，GitHub 授权走 Personal Access Token（PAT）轻量方案
- **主存储**：方案 C。放弃标准 OAuth App 流程（该流程第 4 步需要在服务器端用 client secret 换取 token，与纯静态的 GitHub Pages 部署冲突）。改为**用户自行在 GitHub 设置里生成一个 Personal Access Token（细粒度 PAT，仅授予该 token 对目标仓库的读写权限），粘贴到应用的设置页保存**，之后前端直接用这个 token 调用 GitHub API 读写数据文件（或 Gist）。
  - 优点：全程纯前端即可实现，不需要任何后端/无服务器函数中转，实现成本最低。
  - 代价：用户需要自己去 GitHub 走一遍生成 token 的操作，体验上比"一键登录"多几步；且 token 需要用户自己妥善保管、到期后自己去 GitHub 续期或重新生成。
  - 安全建议：引导用户创建**细粒度（Fine-grained）PAT**并只勾选目标仓库的读写权限，而不是给一个能访问账号下所有仓库的旧版 Classic Token，降低一旦泄露的影响面。
- **兜底/备份**：方案 B，保留手动导出/导入 JSON 的功能，作为离线备份和迁移手段——即便 token 失效、过期或用户想脱离 GitHub 单独备份一份，也有退路。
- localStorage（方案 A）仍作为**本地缓存层**存在（避免每次操作都请求 GitHub API），但不再是唯一数据源，登录后以 GitHub 上的数据为准，本地只做缓存和离线时的兜底展示。
- 实现上需要考虑：设置页里 token 的输入与本地存储方式（PAT 本身也是敏感信息，存储时同样需要注意，不应明文暴露在页面日志或分享截图里）、API 调用频率限制下的本地缓存/防抖策略、写入冲突处理（如两台设备短时间内先后写入时如何合并或取最新）。

## 4. 信息架构

```
首页（事件列表）
 ├─ 顶部：新建事件入口
 ├─ 筛选/排序切换（默认：按超期程度排序）
 ├─ 事件卡片列表（按分类可选分组显示）
 │   └─ 每张卡片：事件名 / 分类 / 距今天数 / 状态色 / 一键打卡按钮
 └─ 点击卡片进入详情页

事件详情页
 ├─ 基本信息：名称、分类、期望周期（可编辑）
 ├─ 历史记录列表（时间倒序）
 ├─ 统计信息：平均间隔 / 最长间隔 / 最短间隔
 ├─ 操作：一键打卡 / 补录历史日期 / 编辑 / 删除

新建/编辑事件
 ├─ 名称
 ├─ 分类（选择预设或自建）
 ├─ 期望周期（可选填）
 └─ 初始记录（可选：补录起始日期）

数据管理（次要页面）
 ├─ 导出数据（JSON）
 └─ 导入数据（JSON）
```

## 5. 数据结构草案

```json
{
  "events": [
    {
      "id": "uuid",
      "name": "剪头发",
      "category": "个护美容",
      "expectedIntervalDays": 45,
      "records": [
        { "date": "2026-08-01" },
        { "date": "2026-06-20" },
        { "date": "2026-05-10" }
      ],
      "createdAt": "2026-05-10"
    }
  ],
  "categories": [
    { "name": "医疗健康", "icon": "🩺", "isCustom": false },
    { "name": "个护美容", "icon": "🧴", "isCustom": false },
    { "name": "居家清洁", "icon": "🏠", "isCustom": false },
    { "name": "社交家庭", "icon": "👨‍👩‍👧", "isCustom": false }
  ]
}
```
- `records` 按时间倒序存放完整历史，最新一条即"上次完成时间"。
- 当前"已过天数"、状态（正常/该做了/超期）均由前端根据 `records[0].date` 与 `expectedIntervalDays` 实时计算，不落盘存储。

## 6. MVP 范围界定

**MVP 包含：**
- 第 2 节中全部 6 项已确认功能（历史记录、期望周期与状态、4 分类+emoji图标、一键打卡+补录、按超期程度排序展示、无周期事件视觉降权）
- GitHub 作为数据存储（方案 C，PAT 轻量授权方式）+ JSON 导出/导入兜底（方案 B）+ localStorage 本地缓存
- 设置页：粘贴/更新 Personal Access Token

**MVP 不包含（后续迭代再考虑）：**
- 主动推送提醒
- 数据可视化图表（间隔趋势图等）
- 多用户/账号体系（GitHub 账号本身即用户身份，不再单独设计账号系统）
